## 今回発見・修正した課題

1. **「CI成功」の範囲が不足していた。** GitHub ActionsのNode.jsテストが手書きで列挙されており、新しい暫定順位・地図・欠測テストは未実行だった。全MJS構文検査と全Nodeテストの自動発見へ修正。初回は[CI #39751497371](https://github.com/moyashimisosoup/koredoko/actions/runs/39751497371)で**342件中341成功・1失敗**を検出。町丁目の代替参照点を追加後、表示施設10件なのに旧テストが6件と期待していた点を修正した。
2. **静的テストだけでは操作できると断定できなかった。** Playwright ChromiumでPRのHTMLをlocalhostで開いて動かすブラウザテストを追加。PC **1280×800**、モバイルタッチ **390×844**を実行。[操作検証CI #39751927001](https://github.com/moyashimisosoup/koredoko/actions/runs/39751927001)はPython 3.11・3.13、Node全件、ブラウザの**全4ジョブ成功**。
3. **入力エラー後に旧広告の結果が残る危険。** 無効なJSONを送ると先の広告から得た候補・地図が残り、現在の入力結果と誤解させる。失敗時は旧の候補・地図・引用・詳細を消去して入力訂正を促すよう画面を修正。Chromiumによる正常復帰確認も完了。
4. **検証の重複コスト。** オフラインの高速テストはDraft PRの毎コミット実施。重いブラウザテストは今回1回実施済みのエビデンスを保存し、次回はDraftをReady for reviewにするゲートで再実行するよう変更。実機ブラウザの確認と駅出口の精密調査を混同しない。

### 過剰検査を防ぐ停止条件

- iPhone Safariはまず**代表的な1つの入力動線でG3を一巡**。重大な崩れがなければ全端末・全物件・全地図ピンの完全試験を要求しない。
- 致命的な不具合は「旧結果の残留」「7候補が理由なく消える」「参考点を実際の入口と誤認させる」「入力できない」「画面の見切れやピン重複で操作不可能」。発見した項目だけ修正して再検証。
- 駅出口の全件確認、ひばりヶ丘全42/70経路の測定、未校正の遠回り係数の細かな最適化は、**今回のブラウザ操作検収に要求しない**。
- 将来の独立Top1/Top3評価には広告正解を事前固定し、正解建物や住所を特徴量に混入させない。結果を見た後に調整した係数は同じ母集団の独立評価に使わない。
- 試験データH01〜H03のみの段階で、一般地域の広告での性能が証明されたと表現しない。
