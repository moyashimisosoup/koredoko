# APP-023「koredoko」P2 複数条件総合照合エンジン v0.1

2026-10-19 JST｜正本 `moyashimisosoup/koredoko`｜実装: `src/condition_matcher.mjs`｜実験UI: `compare.html`

## 判断・前回からの方針変更

以前の駅代表点からの単純な徒歩半径の共通領域は、[公開UR4件で街区参照点が2/4件しか含まれない](BLIND_TRIAL_RESULTS_2026-10-19.md)ことが判明した。これを物件候補の**自動除外フィルタとして使わない**。

先に複数の独立目的地の徒歩条件と建物属性を総合し、**候補ごとの一致・不一致・判定保留を比較するエンジン**を作る。ただし駅出口や実建物の距離は品質認証が終わっておらず、現時点の比較は合成データから始める。実際の非公開個人住戸の住所特定は対象外。

## 計算仕様

- 文字列の施設名が似ていても同一扱いにせず、運営主体または入力側で確認された`place_id`を物理目的地のグループキーとする。
- 同じ駅の別路線を複数条件として重複得点しない。徒歩分数に食い違いがあれば、その目的地は比較から保留する。
- 広告徒歩`m`分を道路距離 `(m-1)×80 < distance ≤ m×80` の区間とする。幅表示は下限分数〜上限分数の全区間を扱う（例：7〜11分なら480〜880m）。
- 品質が確認された**歩行者向け道路距離**のみ比較上の強い一致・不一致に用いる。必要条件：`entrance_verified=true`、`graph_pinned=true`、端点道路吸着 ≤25m。これらは**データ提供者の品質フラグ**で、今のPoCが独立に検証したものではない。実証前に確定表示へ昇格させない。
- 強い距離が公告区間内なら`match`（+3点）、区間外40mを超えたら`conflict`（−4点）、区間境界に近ければ`review`（0点）。
- 駅代表点や施設代表点からの直線距離は`hint`（+1点）または`caution`（−1点）止まり。**直線距離では一致を確定できない**。
- 築年・階数が出典確認済みのとき一致+2、不一致−3。未確認なら仮の一致+1、不一致−1。完全欠損や品質不足は0点。
- 同じ施設について独立した複数の強い計測値が大きく食い違う場合、都合のよい方を選ばず`unknown`とする。
- 得点は透明性のある**開発用・参考順序の指数**であり、校正された正解確率、統計信頼度、確定判定ではない。最高点が1件でも`candidate_selection_verified=false`、候補が情報欠損のみなら`abstain`。
- 入力上限30条件・50候補。画面はブラウザ内で処理し、JSON内容をHTML実行せず`textContent`で描画。外部APIとの通信なし（同一オリジンの架空JSON取得を除く）。

## 架空サンプルと実験設計

`examples/synthetic_multicondition_v0.1.json`には実在しないA駅、B駅、スーパーC、2012年築、5階建を含み、候補A〜Dを比較する。元の6つの広告条件は「A駅の別路線」が重複するため、独立する5条件（異なる徒歩目的地3＋建物属性2）として扱う。

期待される結果は**候補A > 候補C > 候補B > 候補D**（参考順位、アプリ本体の実世界推定結果ではない）。候補Aは5項目の強い一致を持ち、候補Bには道路距離および階数の不一致、候補Cは弱い参考一致、候補Dは情報欠損だけを持つ。

## 残る課題と次の作業

1. OSM／PLATEAU等の権利・出典を確認し、まず**公開名称付き集合住宅や架空建物**から候補の建物属性を用意する。個人の居住先や非公開の所在地特定には使用しない。
2. Valhalla等の歩行ネットワークから実際の駅出口・施設までの経路距離を計算する。R06〜R08の精度ゲートが未達なら各条件は弱い参考または保留。
3. 同一広告や同じPOIソースを複数の独立根拠として加点しない規則を、データ収集段階で確定する。
4. 位置推定性能は、開発に使ったサンプル以外の独立した公開物件で評価する。以前のUR4件はチューニング用とし、最終テストから除外する。
5. 入力点検 `index.html` と照合画面 `compare.html` を接続する正式なアダプタ、地図と候補範囲の視覚化、PC/iPhone実機検証、Pages公開は別工程。
